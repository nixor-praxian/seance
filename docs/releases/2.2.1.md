# 2.2.1 — minimized panes excluded from `organize`

## Summary

`seance organize` moved minimized windows. Because the watcher runs `organize`
on every display-set change, connecting or disconnecting a display restored
every minimized pane from the Dock and tiled it alongside the rest. This
release restricts `organize` to active panes, matching the behaviour `arrange`
has had since 2026-08-15.

## Impact

Any user running the watcher (`seance watch`, or the `com.seance.watcher`
launch agent) with one or more minimized Ghostty windows. No data loss; the
effect was confined to window geometry and visibility. Minimizing a pane was
not durable across a display change.

## Root cause

`runOrganize` built its work list from every live pane. Minimized panes are
live — they hold a TTY and appear in perception — so they were included.

`setWindowBounds` focuses each target before positioning it, which is required
to migrate windows onto the current macOS Space; without it, an AX position-set
on an off-Space window silently strands the window. Focusing a minimized window
restores it. Every minimized pane in the work list was therefore un-minimized as
a side effect of being positioned.

The exclusion this requires already existed. `splitByVisibility` had a single
call site, in `runArrange`. `organize` — the verb the watcher invokes on display
changes — did not call it. The 2026-08-15 work established the constraint
correctly ("a minimized pane must be excluded *before* `setWindowBounds`, not
after") and applied it to one of the two verbs.

## Resolution

`runOrganize` now calls `splitByVisibility` and tiles only the active panes.
Painting is unchanged and still covers every live pane: OSC writes reach a
minimized window's TTY, so a restored window is already the correct colour.

Skipped panes are reported rather than dropped silently, and the pane count is
now stated against active panes rather than all live panes:

```
organized 6/6 pane(s), painted 8 (dark)
  main            3x2   api, web×2
  external.left   2x1   infra×2
minimized (not tiled): docs, tooling×2
```

Diff: 14 insertions, 2 deletions in `src/cli.ts`.

## Known limitations

Two behaviours remain unaddressed in this release.

**Hotplug reflows every active pane.** The watcher's display-change handler
runs an unconditional `organize`, re-deriving a layout from scratch on every
transition. This is current design, not a defect, but it re-answers "where
should everything go?" at the least useful moment. The intended replacement is
presets keyed to the display set, so that connecting a display applies a
previously saved arrangement rather than an improvised one. Designed, not built.

**The display-change debounce does not debounce.** The handler sleeps a fixed
3 seconds, runs `organize`, then stores the signature captured *before* the
sleep. It never re-reads geometry to confirm the display set has settled.
macOS emits several transitions while a newly connected display is
negotiated, and each is treated as an independent event, so one physical
connection produces several full reflows. Observed: three reflows from a single
connection. The handler is additionally gated on `tick % 5`, which `CLAUDE.md`
identifies as an anti-pattern — a tick is one iteration of a loop performing
`osascript` and `lsof` calls, not a wall-clock interval, so detection latency is
variable.

The fix for the second item is a settle loop: on detecting a change, poll
geometry until it is stable for a fixed wall-clock interval, act once, and
record the signature that was acted upon.

Interim mitigations, if the reflow is disruptive: a `state.watchReflow: false`
flag to disable the display-change handler while retaining auto-painting and
the Claude Code theme self-heal, or unloading the watcher entirely and losing
both.
