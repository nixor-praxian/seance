# 2.2.4 — display identity moves to the UUID

## Summary

Every part of seance that named a specific display used `CGDirectDisplayID`,
which is not stable across a reconnect on a machine driven by DisplayLink. This
release moves display identity to the per-display UUID — the same identity macOS
itself uses — and moves persisted geometry from `visibleFrame` to the full frame.

## Impact

Anyone using a DisplayLink dock, which is the only supported way to drive more
than one external display on an Apple Silicon Mac with a single controller. Two
symptoms, both previously reported as separate bugs:

- Reconnecting a familiar display arrangement re-tiled everything, because
  2.2.3's "leave a known arrangement alone" rule could never recognise one.
- A group with a saved target display silently fell back to the main display on
  every replug.

## Root cause

A DisplayLink display is not attached to the GPU. `DisplayLinkUserAgent` creates
a virtual display, captures its framebuffer, compresses it and sends frames over
USB to a decoder in the dock. Because the display is *created* by a userspace
process rather than enumerated from a video port, macOS assigns it a fresh
`CGDirectDisplayID` every time that process brings it up. Measured on the same
two physical panels: `25, 26` in the morning, `27, 28` that evening.

`knownDisplaySets` signatures and `group.displayId` both keyed on that number.

## Resolution

`ScreenInfo` gains two fields:

- `uuid` — from `CGDisplayCreateUUIDFromDisplayID`. **This function lives in
  `ColorSync.framework`, not CoreGraphics**; a CoreGraphics lookup fails with a
  bare *symbol not found*. Read via JXA in `listScreens`, no new dependency and
  no extra process. Degrades to an empty string, in which case the signature
  falls back to the id.
- `frame` — the full frame. `visibleFrame` shrinks and grows when the Dock
  changes edge or toggles auto-hide, which was indistinguishable from a display
  being plugged in.

Display-set signatures are now `uuid:x,y,w,h` per display. Groups store
`displayUuid`; `pickScreen` tries UUID first and falls back to `displayId` for
state written before this release. Signatures in the old format are pruned on
the next write, costing one reflow.

`seance screens` shows the UUID beside the id and states which of the two is
stable. `doctor.sh` reports whether the DisplayLink agent is running.

## Evidence

`com.apple.windowserver.displays` holds **40 remembered display arrangements**
on the audited machine, every one keyed by UUID. The left panel's UUID recurs in
7 of them, across 2-, 3- and 4-display setups at four different origins, while
its numeric id changed at least once in a single day. That database is also why
macOS restores window positions correctly across a reconnect — and why seance
overwriting that restore was worse than doing nothing.

## Known limitations

The two panels share vendor (`19083`), model (`48178`), size, and even their
name — macOS reports both as `BASE CASE`, disambiguated only by an assignment-
order suffix in which *(2)* is the left one. Their EDID serials differ
(`0x01010101`, `0x01010160`) but are visibly synthetic and were not verified as
stable. The UUID is the only identity that separates them reliably.

The unplug direction still inherits 2.2.3's assumption that macOS restores well
in both directions. Confirmed for reconnection, untested for disconnection.

## Verification

- `npm run typecheck` — clean. `npm test` — 184 tests, all passing.
- `seance screens` and the signature builder exercised against the live
  three-display arrangement; the built-in now reports its full `1728x1117`
  frame rather than the Dock-dependent `1728x1079` visible frame.
- **The reconnect behaviour is unverified.** It needs a physical unplug and
  replug, with `watcher.log` showing `known display arrangement — leaving
  macOS's restore alone` where an `organized` line used to appear.
