# 2.2.5 — theme assignment settles instead of thrashing

## Summary

`assignThemes` could reassign a repo's colour on every watcher pass, forever.
One real log accumulated **31,025 identical reassignments** of a single repo,
each one a `state.json` write. Assignment now settles, and a collision is
decided by incumbency rather than alphabetical order.

## Impact

Anyone with more live repos than assignable theme pairs, or with two live repos
sharing a pair. Symptoms: colours shuffling between panes, an established repo
losing its colour to one just seen, a watcher log growing without bound, and
continuous state writes.

Per-repo colour is the whole point of the tool, so a colour that will not hold
still is a primary failure, not a cosmetic one.

## Root cause

Two defects compounding.

**The fallback assigned an already-worn pair.** When a repo lost a collision it
picked a replacement:

```ts
const pick = ring.find(p => !pairsInIdentity.has(p))
          ?? ring.find(p => !pairsWornByLive.has(p))
          ?? ring[assignIndex % ring.length]!;   // already worn by someone
```

With no free pair, the third branch handed back a colour somebody else was
wearing — so the repo was a collision loser again on the next pass, and the pass
after that. Nothing broke the cycle.

**The collision keeper was alphabetical.** `colliders[0]` after sorting, so a
transient repo evicted an established one purely by sorting earlier. Observed
live: a pane whose working directory wandered into `mnemosyne` repeatedly took
`Ayu` from `seance`, because *m* precedes *s*.

## Resolution

An established repo is no longer reassigned when the ring has nothing free — it
keeps what it has. A duplicate colour is stable; an endlessly reassigned one is
not. A repo seen for the first time still takes a round-robin pair, so a new
pane is never left unpainted.

`IdentityEntry` gains `assignedAt`, and collisions are decided by pinned first,
then incumbency, then name. Entries written before this release have no stamp
and are treated as oldest, so existing assignments win against newcomers.

A collision loser still drops `pinned` — a pin that lost is not a pin. That was
pre-existing behaviour, and the test suite caught an attempt to change it.

## Ring capacity

Assignment can only be collision-free while live repos do not outnumber
assignable pairs. The registry held 9; five further pairs were selected from
Ghostty's 463 bundled themes by auto-pairing on name, validating polarity by
background luminance, scoring contrast repairs, and then choosing greedily for
maximum OKLab distance from every already-registered background — because the
ring's job is telling panes apart at a glance:

| pair | dark | light | repairs |
|---|---|---|---|
| Github High Contrast | GitHub Dark High Contrast | GitHub Light High Contrast | 2 |
| Gitlab | GitLab Dark | GitLab Light | 3 |
| Zenbones | Zenbones Dark | Zenbones | 5 |
| Neobones | Neobones Dark | Neobones Light | 6 |
| Iceberg | Iceberg Dark | Iceberg Light | 13 |

Only five cleared the distinctness threshold — dark terminal backgrounds cluster
tightly, and pairs that are merely *different* are not *distinguishable*.

These were added via `seance theme register`, which writes to `state.themes`.
`BUILTIN_THEME_PAIRS` and `docs/themes-preview.html` are deliberately untouched:
the curated set is a product decision, and promoting these into it would mean
updating the preview page too.

## Verification

- `npm run typecheck` clean; **186 tests**, including two new regressions: that a
  second pass over an exhausted ring produces no changes at all, and that an
  incumbent keeps its pair against an alphabetically-earlier newcomer.
- Observed on the live machine: 45 seconds of steady state produced **one**
  reassignment (a repo claiming a newly-registered pair), against continuous
  flip-flopping before. All nine live repos now hold distinct colours.
