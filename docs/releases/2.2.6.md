# 2.2.6 — verified placement, and windows stay on their display

## Summary

`setWindowBounds` reported a window placed whenever the AppleScript ran, without
checking anything moved. It now reads the applied rect back and compares. Two
consequences follow: a window that loses the title-sentinel race is retried
instead of silently abandoned, and windows Ghostty enlarges past their cell are
nudged back onto the display they were assigned to.

## Impact

Observed on a three-display setup: `seance arrange` printed `13/13` while one
pane sat untouched, straddling two tiles on the wrong display. A second run
placed it. Separately, two panes hung 62px past the bottom of an external
display and onto the laptop.

## Root causes

**Unverified placement.** The apply script appended an index to its result
string after calling `set position`, so success meant "the script ran", not "the
window moved". A pane whose title is being rewritten under us — anything with a
spinner — can lose the sentinel race, and the failure was invisible. Because the
window counted as placed, the five-round retry loop never reconsidered it.

**Cell quantization.** Ghostty snaps a window to whole character cells, so a
requested rect is rounded to whatever the pane's font size permits. Measured:
548x540 → 548x602, 823x440 → 823x502, 432x1079 → 443x1021. Growth is not
optional and not predictable from the cell alone. A grown bottom-row window
extends past the display edge, and macOS lets it hang onto the next display.

**A fictional floor.** `minPaneHeight` defaulted to 256, which nothing can
render.

## Resolution

The apply script now reads position and size back in the same pass. A window
counts as placed only if its origin is within 40px of the request — a tolerance,
because macOS declines to seat a title bar flush against a display's top edge,
which shows up as a consistent 25px push down. Size is deliberately not
compared, since quantization makes exact size unattainable.

Windows that came back larger than their cell are collected as `drift` and, in a
second pass, nudged up and left so their far edge lands where the cell's did.
They may now overlap the neighbour above; they no longer leave their display.
`arrange` and `organize` print what was enlarged rather than leaving it to be
discovered visually.

`minPaneHeight` defaults to 440, and an existing value below that is raised on
load. A deliberately higher one is left alone.

## Measured

On the live three-display arrangement, across all 14 active panes:

| | before | after |
|---|---|---|
| windows crossing a display boundary | 2 | **0** |
| overlapping pairs | 10 | 4 |
| total overlap | 262,111px² | 133,002px² |

The four remaining overlaps are upward, within a display, and are the deliberate
trade: quantization means some overlap is unavoidable, and overlapping the pane
above is better than hanging off the screen.

## Known limitation

Exact tiling is not achievable. A pane's cell size is rounded to its own font's
character cell, which differs per pane, so gaps and overlaps of up to one cell
are inherent. They are now reported instead of silent.
