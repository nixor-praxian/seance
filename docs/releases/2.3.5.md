# 2.3.5: pane titles don't get stuck on a seance marker

## What you'll notice

**Titles come back.** seance finds a pane's window by writing a marker into
its title, like `⎈seance-read:mwfa7aet:12`, looking for that marker through
macOS Accessibility, and then writing a readable title back (usually the
repo name). When the lookup itself failed, the last step never ran. Busy panes
didn't show it, because the shell or Claude Code rewrites its own title soon
enough. Idle panes kept the marker indefinitely, so a whole row of windows
could read `⎈seance-read:…` instead of the project they belong to.

Now the title is written back whether the lookup worked or not.

## Do I need to do anything?

If your titles are already stuck, run `seance windows --probe` once. It
relabels every pane with its directory name.

If the watcher log (`~/.config/seance/watcher.log`) contains "osascript is not
allowed assistive access", the watcher can't see windows at all. Find the
`node` it runs under (`ps -o command= -p $(launchctl list | awk
'/com.seance.watcher/{print $1}')`), switch it on under Accessibility in System
Settings, and restart the watcher with `launchctl kickstart -k
gui/$(id -u)/com.seance.watcher`.

## Under the hood

Four functions in `ghostty.ts` write a marker title: `setWindowBounds`,
`focusTty`, `probeWindows` and `windowStatesByTty`. Each ran the
Accessibility read and then the cleanup in sequence, so an exception from
`osascript` skipped the cleanup. They now restore titles in a `finally`
block (`probeWindows` in a `catch` that rethrows, since its normal cleanup
labels panes with data computed after the read).

The common trigger is a Node upgrade. macOS grants Accessibility per binary,
and with nvm every Node version is a different binary at a different path. A
watcher started by launchd under a Node that hasn't been allowed gets error
-25211 from System Events on every read. It keeps painting, because colours
go straight to each pane's TTY, so nothing looks wrong apart from the titles.
